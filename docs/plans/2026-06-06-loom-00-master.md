## 0. What Loom is (one paragraph)

Loom is the **rebase-based orchestration layer** on top of quilt (merge-based
combination probe) and rightwayc (doctrine + skills + per-task reflection). quilt
answers *"which combinations of branches are mutually viable"* (cheap, merge-based,
order-insensitive). Loom answers *"given a viable combination, what ordering makes
it all-commits-green and bisectable"* (expensive, rebase-based, order-sensitive),
and owns the tiered promotion (`staging` → `next_staging`), the long-lived
design-alternative branch zoo, and the agent loops that keep it all green.

## 1. Where the code lives (locked decision)

Loom has **no dedicated repo**. Per spec §11 and the confirmed structural decision,
it is split across the two repos it extends:

| Half | Repo | Home | Rationale |
|------|------|------|-----------|
| **Deterministic engine** (§6.1–6.10, §4 data model, §10 scheduler) | `quilt` | new modules under `src/quilt/loom/`; plans under `docs/plans/loom-*.md` | Loom *is* the rebase layer atop quilt; it reuses quilt's gitio, db, gates, llm, scheduler, candidate, backprop primitives directly (in-process import, not subprocess). |
| **Agent loops** (§8 roles, §7 contract surface, §9.4 leak gate) | `rightwayc` | new skills under `skills/`; workflow under `.claude/workflows/`; plans/specs under `docs/superpowers/` | Spec §8: "Agents are packaged as rightwayc commands/skills (their home)." Mirrors the existing mergeq workflow + thin-agent pattern. |

The engine **invokes** agents through the universal decision contract (§7): a configured
shell command (`claude -p --model <tier>`), exactly the mechanism quilt's `llm.py`
(`run_json`, `run_edit`) already implements. The rightwayc skills are the *content*
loaded into those agent invocations; the engine never imports rightwayc Python.

> **New top-level package, not edits to quilt's existing modules.** Loom adds
> `src/quilt/loom/` and a `loom` console-script entry point. It *imports* and reuses
> `quilt.gitio`, `quilt.db`, `quilt.gates`, `quilt.llm`, `quilt.resolve`,
> `quilt.candidate`, `quilt.backprop`, `quilt.scheduler` but does not rewrite them.
> Quilt's own CLI and tests stay green throughout.

## 2. Governing principles → enforcement hooks

The six spec §2 principles are not prose; each maps to a concrete, testable guard
that the phase plans implement. This table is the conformance checklist.

| # | Principle | Concrete enforcement (phase) |
|---|-----------|------------------------------|
| 1 | Increment-set is source of truth; branches are projections | `increment` + `dep_edge` tables (§4); every integration branch is `materialize(sort(...))`; force-push is a first-class op (P2, P3). |
| 2 | Deterministic by default; LLM only at a named decision | Every LLM call goes through one `loom.decide()` wrapper around `quilt.llm.run_json`/`run_edit`; a clean clear of the ladder makes **zero** decide() calls (asserted in tests, P2/P4). |
| 3 | Green by truncation, never by silent fixing | Linearizer publishes only the **maximal green prefix**; everything past the first red seam is parked as a work item, never materialized (P2). |
| 4 | No responder self-certifies | Every responder result re-enters at the **top** of the gate ladder; the auditor re-runs the emitter (P1 gates the cache; P5 enforces re-entry). |
| 5 | Coverage is the spec | Coverage gate is a ladder rung **and** validates that seam tests exercised the dep they could trip (P4, feeds P2's inferred DAG). |
| 6 | Safety rails are gates, not conventions | No component auto-pushes; propose-push gate surfaces for approval, verifies `hila-shemer` (not `Majestic`) in the URL via rightwayc's `green_verify.py`, and emits patch artifacts on block (P3). |

## 3. Tier model (spec §3) — concrete refs

| Tier | Git ref | Advances by | Mutable region | LLM cost |
|------|---------|-------------|----------------|----------|
| **zoo** | `refs/loom/zoo/<inc>` | continuous rebase on moving `next` | whole branch | maintenance loop (P7) |
| **staging** | `refs/loom/staging` (local, never pushed) | force-push/reorder **above the frozen floor only** | suffix above `next_staging` tip | seam-search per promotion (P2) |
| **next_staging** | `refs/loom/next_staging` → propose-push (P3) | **fast-forward only** from staging | append-only | stress (`long`) gate at milestones |

- `next_staging` is a **frozen floor**: staging may rewrite only the suffix above it.
  The seam-search working set *is* that mutable suffix; it shrinks from below as
  milestones validate (P2 + P3).
- FF into `next_staging` preserves commit identity → quilt's per-commit gate cache
  stays hot → the only marginal work at promotion is the `long` gate (P3).
- A **milestone** defaults to the tip of a fully-absorbed increment (decision §13,
  confirm before P3 ships).

## 4. Data model (spec §4) — additions over quilt's schema

Loom **adds** tables to the *same* SQLite DB quilt already uses (single-writer,
crash-durable, content-keyed, idempotent). It does **not** alter quilt's existing
tables. New tables live in `src/quilt/loom/schema.py` (applied additively next to
`quilt.db.SCHEMA`).

| Table | Purpose | Spec ref | First built in |
|-------|---------|----------|----------------|
| `increment` | the source of truth: id, tier_target, patches(repo→patch), priority_class, deps(hint), dod, base, oracle_ref, status, stability, patch_id | §4.1 | P2 |
| `dep_edge` | inferred DAG `X→Y` ("X red unless Y precedes"), durable until X or Y changes | §4.2 | P2 |
| `commit_gate` | per-commit gate cache `(commit_tree_sha, gate) → result` — distinct from quilt's per-merge-point `gate_status` | §4.3 | P2 |
| `audit_result` | per gate-ladder execution: expected/actual counts, rebuilt-from-tree proof, coverage∩diff, real-green vs fake-green | §6.1 | P1 |
| `role_journal` | role/task_type-keyed experience: kind, pattern, lesson, recurrence, refs, scope | §4.4, §8 | P6 |

Content objects stay in git under `refs/loom/*`. Every job result is content-addressed
on `commit_tree_sha` (or `patch_id`) and idempotent → a crashed tick recomputes only
what is missing (§10).

## 5. Universal decision contract (spec §7) — one wrapper

All decision hooks call **one** function, `loom.decide(role, task_type, payload)`,
which:
1. retrieves role-local + global journal context (§9.2; stub returns global-only until P6),
2. shells out via `quilt.llm.run_json` (classifiers/attributors) or `quilt.llm.run_edit`
   (resolver/fixer/debugger/porter) using the configured `claude -p --model <tier>` cmd,
3. **re-runs the deterministic emitter** that produced the signal to verify the result,
4. returns the parsed result or loops/escalates.

No model output is trusted without the deterministic re-check (principle §2.4). This
wrapper is the single seam between the quilt-side engine and the rightwayc-side skills:
the `<tier>` model and the prompt/skill name are config, not code.

## 7. Scheduler & concurrency (spec §10) — cross-cutting

Loom runs jobs over a **`git worktree` pool**, not a monolithic tick. Long jobs (stress,
big composition) run in parallel worktrees; the only serialized point is the per-ref
write at promotion (git enforces per-branch exclusivity). This is built incrementally:

- P1/P2 introduce `loom/worktree.py` (a pool that hands out detached worktrees and
  reaps them) and reuse quilt's `scheduler.tick` K-bound for concurrent heavy tests.
- P2 adds the **reflow epoch**: freeze the solved plan for an epoch; agents complete
  rebases against the frozen plan; results are accepted only if the epoch has not
  rolled, else re-queued. Prevents thrash under continuous force-push.
- All jobs idempotent, keyed on tree-hash, crash-resumable (principle §2 / §4).

The scheduler is not a separate phase doc; its pieces are built where first needed
(pool + epoch in P2) and referenced by later phases.

## 9. Definition of done (whole programme)

Loom is done when: an arbitrarily large set of viable increments can be composed into
an all-commits-green, bisectable `staging`; a stress-validated prefix is fast-forwarded
to `next_staging`; the zoo is kept green against a moving `next` by the agent swarm;
every promotion is gated by a real (auditor-certified) green-on-full-CI signal; and no
remote is ever auto-pushed (every push is a surfaced, `hila-shemer`-verified proposal).
Each phase doc carries its own narrower DoD.
